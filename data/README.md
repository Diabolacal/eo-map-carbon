# New Eden point-cloud artefact

Slim static handoff for Milestone 1B. The Carbon executable does not open
SQLite, does not call ESI, and does not load the EO-Map web app.

## Files

- `new_eden_systems.bin` — little-endian `NEDEN1B` table of known-space id / name / Contract A XYZ
- `new_eden_systems.manifest.json` — provenance, AABB, and hub anchors

## Provenance

Generated by `scripts/export-new-eden-systems.py` from the sibling EO-Map
Contract A universe database:

```
C:\dev\eo-map\eve-frontier-map\public\map_data_eo_3464040.db
```

That database is EO-Map's pinned SDE 3464040 artefact (builder 1.5.0). It is
the same file the live map parses in `universeDbParse.ts`. This export does not
re-read the SDE zip.

Pinned source SHA-256:

```
874262496556d933bbbc184cdec8f469660f6c1108b21e25f0481475b68eba81
```

Regenerate (requires the sibling EO-Map checkout):

```powershell
python .\scripts\export-new-eden-systems.py
```

## What is included

5,485 New Eden known-space systems (`id` 30000000–30999999, `hidden = 0`).

The Contract A table also contains 2,604 Anoikis / W-space systems. EO-Map
draws those too, but they sit in a separate cluster about 1,300 LY away and
are not part of the default New Eden framing. They are omitted here.

## Coordinates

The binary stores Contract A `position_x/y/z` unchanged (light years after
EO-Map's builder remap `(raw.x, raw.z, raw.y) / 9.46e15`).

The Carbon host applies EO-Map's live display mapping before the GPU:

```
scene = (db.x, -db.z, -db.y)
```

Vertices are not recentred. The camera target is the measured New Eden AABB
centre. There is no extra scale.
